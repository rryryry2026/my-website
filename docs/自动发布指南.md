# 自动发布指南

目标：在本地管理端改完内容后，运行一条命令，自动完成 **本地构建校验 → 提交 GitHub → GitHub Actions 构建 → 同步到阿里云服务器**。

```text
本地 npm run admin 改内容
        │
        ▼
npm run publish
        │  构建校验、展示变更、确认
        ▼
git commit + git push origin main
        │
        ▼
GitHub Actions（.github/workflows/deploy.yml）
        │  npm ci + npm run build
        ▼
SSH / rsync 同步 dist/
        │
        ▼
阿里云 /opt/my-website/dist  →  Nginx  →  网站更新
```

---

## 一、一次性配置

以下步骤只需要做一次。

### 1. 生成部署专用 SSH 密钥

在本地 Git Bash 中执行：

```bash
ssh-keygen -t ed25519 -C "github-actions-deploy" -f ~/.ssh/tulip_deploy -N ""
```

会生成两个文件：

- `~/.ssh/tulip_deploy`：私钥，**只放到 GitHub Secrets，绝对不要提交到仓库**
- `~/.ssh/tulip_deploy.pub`：公钥，放到服务器

Windows 下路径是 `C:\Users\毛林昊\.ssh\tulip_deploy`。

> 这里故意不设置密钥密码，因为 GitHub Actions 无法交互输入密码。私钥只保存在 GitHub Secrets 中。

### 2. 把公钥加到服务器

如果本机有 `ssh-copy-id`：

```bash
ssh-copy-id -i ~/.ssh/tulip_deploy.pub root@121.196.97.18
```

没有的话，用下面这条：

```bash
cat ~/.ssh/tulip_deploy.pub | ssh root@121.196.97.18 \
  "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

验证能否免密登录，并且部署目录可写：

```bash
ssh -i ~/.ssh/tulip_deploy root@121.196.97.18 \
  "test -w /opt/my-website/dist && echo 'deploy key ok'"
```

输出 `deploy key ok` 就说明公钥和目录都没问题。

### 3. 服务器准备

确认服务器安装了 `rsync`：

```bash
ssh -i ~/.ssh/tulip_deploy root@121.196.97.18 "command -v rsync"
```

没有输出就安装：

```bash
ssh -i ~/.ssh/tulip_deploy root@121.196.97.18 "apt-get update && apt-get install -y rsync"
```

确认 Nginx 的网站根目录确实是 `/opt/my-website/dist`：

```bash
ssh -i ~/.ssh/tulip_deploy root@121.196.97.18 \
  "grep -R 'root ' /etc/nginx/sites-enabled/"
```

这台服务器的站点配置在 `/etc/nginx/sites-available/my-blog`，通过 `sites-enabled` 里的软链接生效；当前 `root` 就是 `/opt/my-website/dist`。

> `DEPLOY_PATH` 必须指向 `dist/` 本身，不能指向 `/opt/my-website` 源码目录。工作流会使用 `rsync --delete-after`，如果指向上层目录，会删除源码和依赖。
>
> 当前服务器上 `dist` 的属主是 `www-data:www-data`，工作流会用 `--chown=www-data:www-data` 保持这个属主，Nginx 可以直接读取。

确认 root 允许密钥登录：

```bash
ssh -i ~/.ssh/tulip_deploy root@121.196.97.18 \
  "grep -E '^#?PermitRootLogin' /etc/ssh/sshd_config"
```

结果应该是 `PermitRootLogin prohibit-password` 或 `PermitRootLogin yes`。如果是 `no`，GitHub Actions 无法用 root 登录，需要改成 `prohibit-password` 后重载 sshd，或者新建一个部署用户并把 `DEPLOY_USER` 改成它。

确认阿里云安全组允许 GitHub Actions 通过 SSH 连接服务器：

- 入方向放行 TCP **22**（或你自定义的 SSH 端口）
- 建议只允许密钥登录，关闭密码登录
- 如果之前安全组只放行了你的家庭 IP，需要额外放行 GitHub Actions 的来源 IP，或者临时对公网开放 22 端口并配合密钥登录、fail2ban

### 4. 配置 GitHub Secrets

打开仓库：

```text
https://github.com/rryryry2026/my-website/settings/secrets/actions
```

#### 方式 A：用 gh 命令设置（推荐）

你的电脑已经安装并登录了 GitHub CLI（账号 `rryryry2026`），可以直接执行：

```bash
gh secret set DEPLOY_HOST --repo rryryry2026/my-website --body "121.196.97.18"
gh secret set DEPLOY_USER --repo rryryry2026/my-website --body "root"
gh secret set DEPLOY_PORT --repo rryryry2026/my-website --body "22"
gh secret set DEPLOY_PATH --repo rryryry2026/my-website --body "/opt/my-website/dist"
gh secret set DEPLOY_SSH_KEY --repo rryryry2026/my-website < ~/.ssh/tulip_deploy
```

这样私钥直接从文件读入，不会因为复制粘贴丢换行。

检查是否设置成功：

```bash
gh secret list --repo rryryry2026/my-website
```

#### 方式 B：在网页里手动添加

依次添加以下 Repository secrets：

| 名称 | 值 | 必填 |
| --- | --- | --- |
| `DEPLOY_HOST` | `121.196.97.18` | 是 |
| `DEPLOY_USER` | `root` | 是 |
| `DEPLOY_PORT` | `22` | 否，不填默认 22 |
| `DEPLOY_PATH` | `/opt/my-website/dist` | 是，结尾不要加斜杠 |
| `DEPLOY_SSH_KEY` | `~/.ssh/tulip_deploy` 的完整内容 | 是 |
| `DEPLOY_KNOWN_HOSTS` | 服务器主机指纹（可选） | 否 |

方式 B 需要手动复制私钥内容：

```bash
cat ~/.ssh/tulip_deploy
```

从 `-----BEGIN OPENSSH PRIVATE KEY-----` 一直复制到 `-----END OPENSSH PRIVATE KEY-----`，**包括首尾两行**，粘贴到 `DEPLOY_SSH_KEY`。

PowerShell 也可以用：

```powershell
Get-Content -Raw $HOME\.ssh\tulip_deploy | Set-Clipboard
```

> 不要使用 `Windows 记事本` 另存，容易引入 BOM 或丢失换行。直接复制终端输出即可。

`DEPLOY_KNOWN_HOSTS` 是可选的安全加固。想固定服务器指纹可以执行：

```bash
ssh-keyscan -p 22 121.196.97.18
```

把输出整段放进 `DEPLOY_KNOWN_HOSTS`。不配置时，工作流会自动执行 `ssh-keyscan`。

### 5. 第一次发布

回到项目目录：

```bash
npm run publish
```

脚本会：

1. 在本地跑一次 `astro build`，构建失败会直接停止
2. 展示所有将要提交的文件和 diff 统计
3. 询问提交信息，并再次确认
4. 执行 `git commit` 和 `git push origin main`
5. 打印 GitHub Actions 地址

推送后打开 Actions 页面：

```text
https://github.com/rryryry2026/my-website/actions
```

看到 `Deploy to Aliyun` 变绿后，访问：

```text
http://121.196.97.18:8080
```

以后每次内容更新都会走同样流程。

## 二、日常发布流程

1. 启动管理端：

   ```bash
   npm run admin
   ```

2. 在 `http://127.0.0.1:4400` 修改文章、图片、文案或相册，点击保存。

3. 本地预览确认没问题后，运行：

   ```bash
   npm run publish
   ```

4. 检查脚本展示的变更摘要，输入提交信息，确认。

5. 等 GitHub Actions 跑完（通常 1–3 分钟），刷新线上网站。

> 草稿文章不会出现在线上；取消草稿并发布后才会进入构建。

## 三、发布脚本参数

| 命令 | 作用 |
| --- | --- |
| `npm run publish` | 构建校验 → 展示变更 → 输入提交信息 → 确认 → 提交并推送 |
| `npm run publish -- "site: update about page"` | 使用指定提交信息，仍然会确认 |
| `npm run publish -- --yes` | 跳过交互，使用默认提交信息并自动推送 |
| `npm run publish -- --skip-build` | 跳过本地构建校验，直接提交推送 |
| `npm run publish -- --yes --skip-build` | 最快路径，适合紧急小改动 |

注意：是 `npm run publish`，不是 `npm publish`。

脚本只允许在当前分支为 `main` 时运行。没有修改时会提示并退出。

## 四、手动触发与回滚

### 手动重新部署

即使没有新提交，也可以手动触发一次部署：

```text
GitHub 仓库 → Actions → Deploy to Aliyun → Run workflow → Run workflow
```

或者在本机用 gh：

```bash
gh workflow run "Deploy to Aliyun" --repo rryryry2026/my-website
gh run watch --repo rryryry2026/my-website
```

适合服务器配置调整后重新同步一次。

### 回滚内容

推荐用 `git revert`，不要用 `git reset --hard` 或强制推送：

```bash
git log --oneline
git revert <要撤销的提交编号>
npm run publish -- "revert: rollback content"
```

`git revert` 会生成一个新的反向提交，历史保持完整，Actions 会自动重新部署。

### 服务器上手动兜底部署

如果 GitHub Actions 暂时不可用，可以在本地构建后直接同步。注意 Git Bash 默认不带 `rsync`，需要先用 WSL，或安装 rsync 后再执行：

```bash
npm run build
rsync -az --delete-after --chmod=D755,F644 --chown=www-data:www-data \
  --exclude='.well-known/' \
  -e "ssh -i ~/.ssh/tulip_deploy -p 22" \
  dist/ root@121.196.97.18:/opt/my-website/dist/
```

## 五、常见问题

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `Permission denied (publickey)` | 公钥没加到服务器；Secret 私钥不完整；用户或端口不对 | 重新执行第 2 步；重新复制完整的 `DEPLOY_SSH_KEY` |
| `Host key verification failed` | 服务器重装或指纹变化 | 更新 `DEPLOY_KNOWN_HOSTS`，或删除该 Secret 让工作流重新 `ssh-keyscan` |
| `rsync: command not found` | 服务器没装 rsync | 执行第 3 步安装 |
| SSH 连接超时 | 阿里云安全组未放行 22 端口 | 在安全组入方向放行 TCP 22 |
| `npm ci` 失败 | `package-lock.json` 与 `package.json` 不一致 | 本地运行 `npm install`，把更新后的 lock 文件一起发布 |
| Actions 成功但网站没变化 | `DEPLOY_PATH` 不是 Nginx 实际根目录；浏览器缓存 | 检查第 3 步的 Nginx 配置；强制刷新或换无痕窗口 |
| 网站 403 / 404 | 文件权限或部署目录不对 | 确认 `DEPLOY_PATH` 指向 `dist/`，文件权限为 644 |
| 部署删掉了旧文件 | `rsync --delete-after` 的正常行为 | 不要手动往 `dist/` 里放东西；静态资源都放进 `public/` 再构建 |
| 本地构建失败 | 内容或代码有错误 | 先本地修复 `npm run build`，再发布 |
| `push` 被拒绝（`fetch first`） | GitHub 上有本机没有的新提交 | 先 `git pull origin main` 合并，再 `git push origin main`；有冲突先解决 |

查看失败原因：

```text
GitHub 仓库 → Actions → 点进失败的那次运行 → 展开红色步骤
```

## 六、安全建议

- `DEPLOY_SSH_KEY` 是能登录服务器的私钥，**只放在 GitHub Secrets**，不要写进项目文件、聊天记录或截图。
- 建议关闭服务器 SSH 密码登录：

  ```bash
  sudo sed -i 's/^#\?PasswordAuthentication .*/PasswordAuthentication no/' /etc/ssh/sshd_config
  sudo systemctl reload sshd
  ```

  改之前确认自己的密钥已经能登录，避免把自己锁在外面。

- 当前使用 `root` 部署最省事，但权限较大。后续如果想收紧，可以新建一个只对 `/opt/my-website/dist` 有写权限的 `deploy` 用户，把 `DEPLOY_USER` 改成它。改动前先验证 Nginx 和目录权限。
- 私钥一旦泄露：从服务器 `~/.ssh/authorized_keys` 删除对应公钥，重新生成密钥对，更新 `DEPLOY_SSH_KEY`。
- 仓库是公开的，服务器 IP 和部署路径本身不是密钥，但不要额外提交服务器密码、token 或证书。
